01

认识 Claude Code

它不是又一个代码补全工具，而是一种全新的 AI 助手形态。

AI 编程助手的三代演进

第一代：补全一行输入时猜测下一个词
第二代：补全几行根据上下文生成代码片段
现在：完全代理自主完成整个任务

Claude Code 是完全代理式（fully agentic）的：它一次构建整个功能、编写完整的函数与文件、修复整个 Bug。你只需要说"去做这件事"，它自己会决定怎么做。

完全代理式工作

不是逐行补全，而是像一位工程师那样接收任务、自主拆解、直接交付完整结果。

兼容你现有的一切

VS Code、Xcode、JetBrains、Vim、Emacs——每一个 IDE、每一个终端都能配合。Boris 调侃："Anthropic 有人对 JetBrains 忠贞不渝，'从冰冷的死手里都撬不出来'，但他们也在用 Claude Code。"

任何环境可运行

本地终端、远程 SSH、Tmux 会话——无论你在哪种环境工作，它都能跑，不需要改变现有工作流。

代码永不离开本地

不做索引、不上传、没有存代码的远程数据库、不用你的代码训练模型。代码由你掌控。

如果你没用过这类自由发挥式的编码助手，打开它只看到一个提示词输入框，你可能会想：我拿它干什么？它是一件强力工具（power tool）——可以用来做很多事。

—— Boris Cherny
为什么是 CLI 而不是 IDE？

① Anthropic 内部 IDE 用什么的都有，终端是最大公约数；② 他们近距离看着模型进步的速度，认为年底之前人们可能就不再用 IDE 了——不想在 UI 层过度投入。详见 Q&A。

03

第一步：代码库问答（Q&A）

Boris 最推荐的入门方式，高于其他一切——先提问，别急着改代码。

最重要的一条建议

刚上手 Claude Code 时它太自由、什么都能做——那从什么开始？从对代码库提问开始。不要一上来就用花哨的工具，不要一上来就改代码。

这是 Anthropic 新员工培训的第一课

技术新人入职第一天：学 Claude Code → 下载配置 → 立刻开始对代码库提问。过去技术入职要依赖老员工解答、自己翻代码、学内部工具，大约需要 2–3 周；现在只需要 2–3 天。

过去：2–3 周问同事 · 翻代码 · 学工具
现在：2–3 天直接问 Claude Code

为什么从问答开始？

  • 教会团队成员如何写好提示词
  • 建立能力边界的直觉：Claude Code 能做到什么？哪些事需要你多扶一把？
  • 学会判断什么能一次搞定（one-shot），什么要两枪三枪，什么时候该进交互模式逐步来

零设置、即开即用

问答用法的另一大优点：Claude Code 不做任何索引——没有远程代码库、不上传代码、不训练模型。因此也没有设置流程：下载、启动、立刻提问，不用建索引、不用等待。

问"这个类怎么用"时，它不会只做文本搜索——它会去找实际的实例化示例、翻 Git 历史查这些参数是谁在什么情形下引入的、关联了哪些 Issue，然后给出一份像 Wiki 或文档一样的深入回答。而且系统提示词里没有任何关于"查 Git 历史"的指令——"它知道，是因为模型本身够强。"

Boris 每周一站会前的固定动作

问一句"我这周发布了什么？"——Claude Code 查 Git log、认出他的用户名，输出一份本周交付清单，他直接复制粘贴进周报文档。

关键技巧：写代码之前，先让它思考

常见反模式

直接要求"实现这个 3000 行的大功能"。有时它一次就能做对，但经常做出来的完全不是你想要的。

拿到想要结果的最简单办法：让它先思考。

先规划，经我批准后再动手
在你写代码之前，先头脑风暴几个方案，做个计划，给我过目、等我批准

不需要用计划模式（plan mode）、不需要任何特殊工具——只要开口要求，Claude 自己会明白。

最高频的"咒语"：commit push

Boris 用得最多的提示词
commit push

这句咒语没有任何特别之处，但 Claude 聪明到能正确理解：它会创建 commit → 推送到分支 → 建好分支 → 在 GitHub 上开好 PR。你什么都不用解释——它会自己翻代码、翻 Git log，弄清你们的提交信息格式，然后用正确的方式完成一切。

06

三大高效工作流

"教会 Claude 用工具，再想清楚工作流"——三种经过验证的协作模式。

工作流一：探索 → 规划 → 确认 → 编码 → 提交

探索读代码找根因
规划提几个方案
确认等你拍板
编码按计划实现
提交commit push

这是第 4 章讲过的模式。在提示词里加 ultrathink 可以让 Claude 更深度地思考。

工作流二：测试先行 → 提交 → 编码 → 迭代

写测试如 @app/services/foo 的测试
提交先锁定期望行为
编码让测试通过
迭代直到全部变绿

适合链接/接口尚未实现的场景：测试先写好、预期失败，提交后再让 Claude 实现功能使测试通过。

工作流三：编码 → 截图 → 迭代

给设计稿如 mock.png
编码实现 Web UI
截图对比Puppeteer / iOS 模拟器
迭代2-3 轮近乎完美

把设计稿交给 Claude 实现后，让它自动截图与设计稿对比并自行迭代。

当 Claude 有办法检验自己的工作时——写单元测试、用 Puppeteer 截图、或用 iOS 模拟器截图——它就能自我迭代。给它一张设计稿，第一次就能做得挺好；让它迭代两三次，往往近乎完美。给它一个能看到结果的反馈工具，这是一切的秘诀。

—— Boris Cherny
落地到你的领域

无论单元测试、集成测试，还是 App / Web 截图——给 Claude 一种看到自己产出的方式，它就会自己迭代、越做越好。同时心里要有数：什么任务让它直接写代码、什么先规划、什么要靠迭代，这样才知道怎么提示它。

07

给 Claude 更多上下文：CLAUDE.md

上下文越多，决策越聪明——工程师脑中的系统知识，可以这样交给它。

作为在这个代码库工作的工程师，你脑中装着关于系统架构、历史演进和一切细节的海量上下文。把这些交给 Claude，它做出的决策就越好。最简单的方式就是 CLAUDE.md——一个特殊文件名：

  • 放在项目根目录（即你启动 claude 的目录），每次会话开始时自动读入上下文，本质上是第一条用户消息的一部分
  • CLAUDE.md → 提交进 Git 写一次，全团队共享
  • CLAUDE.local.md → 不提交 只属于你个人的本地配置

CLAUDE.md 里写什么？

常用 Bash 命令

构建、测试、部署等团队高频命令

常用 MCP 工具

团队内部工具的用法说明

架构决策

核心文件位置、重要设计取舍

风格指南

代码风格约定（Anthropic 自己的 CLAUDE.md 就有）

重要文件

在这个代码库干活通常需要知道的

保持简短

太长只会白白消耗上下文，通常也没用——尽量精炼

嵌套目录的 CLAUDE.md：按需自动加载

除根目录外，你可以在任何嵌套子目录里放 CLAUDE.md——当 Claude 在那些目录里工作时会被自动拉入。公司还可以在企业根目录放一份跨所有代码库共享、由 IT 统一管理的 CLAUDE.md。详见下一章的层级全景。

上下文拉取方式全景

Boris 自嘲：做这页幻灯片时特别头疼——因为拉取上下文的方式实在太多。

真实案例：Claude Code 仓库自己就是这样运作的

在 Claude Code 的 GitHub 仓库里，Issue 会被自动打上标签——那是一条斜杠命令加一个 GitHub Action 在跑：Claude Code 执行"给 Issue 打标签"这条命令，人不用管，"帮我们省了很多时间"。

调优上下文的三个思考题

① 可以跑一个提示词改进器来打磨；② 这份上下文给谁用？③ 应该每次都拉取还是按需拉取？跟团队共享还是个人偏好？——花时间调优，做对了性能会大幅提升。

企业策略的两个实战用途

自动批准（给人解锁）

如果全体员工都用同一条测试命令，把它写进企业策略文件——之后任何人运行都会自动批准，不再弹窗。

安全拦截（保代码库安全）

把永不该访问的 URL 加进黑名单——员工无法覆盖，这个 URL 就永远不会被 fetch。

MCP 服务器团队共享

在代码库里提交一个 .mcp.json，之后任何人在这个仓库运行 Claude Code，都会被提示一键安装这些 MCP 服务器。

不知道从哪层入手？

Boris 坦言这张矩阵"有点吓人"——因为官方支持的东西非常多、每家公司的工作流又不同。他的建议是：从「项目共享」层开始——配置写一次、全组受益，形成网络效应：一个人做一点工作，所有人都受益。

快捷键速查（Interlude）

"终端极度极简，有些快捷键很难被发现"——这是一页值得收藏的速查表。

Shift+Tab
自动接受编辑模式编辑自动通过，Bash 命令仍需批准；之后随时可让它撤销。Boris 在"Claude 正在正轨上"或"它在写测试并自行迭代"时开启，省去逐次确认。
#
让 Claude 记住一件事比如它某个工具用错了，打 # 告诉它正确用法——它会自动写进 CLAUDE.md，从此记住。
!
Bash 模式直接运行本地命令，且命令与输出都会进入上下文，下一轮 Claude 就能看到。适合长耗时命令，或你确切知道要做什么时。
Esc
随时安全中断不管 Claude 在干什么，按 Esc 都不会损坏会话。比如它提了 20 行修改、其中 19 行完美只有 1 行要改——按 Esc 说一声，让它重做那 1 行。
Esc×2
跳回历史连按两次 Esc，回退到对话历史中的上一步。
Ctrl+R
查看完整输出展开全部输出——和 Claude 上下文窗口里看到的完全一致。
@
@ 提及文件/文件夹在对话中直接把文件或目录内容拉进上下文。
claude --resume
恢复会话会话结束后恢复指定会话；或用 --continue 直接继续上一次会话。

Claude Code SDK：超级智能的 UNIX 工具

与 CLI 完全相同的代理循环——把 Claude 当作管道里的一个构件来用。

你的代理应用脚本 / CI / 流水线
Claude Code SDK同一套 agent loop
Anthropic / Bedrock / Vertex API
Claude 模型

基础用法：-p 标志

terminal
# 传入提示词、允许的工具（可含具体 Bash 命令）、输出格式
claude -p "summarize these changes" \
  --allowedTools '["Bash"]' \
  --output-format json \
  | jq .result

输出格式可选 json 或 streaming-json（流式处理场景）。

管道玩法

terminal
# git 变更管道输给 Claude 分析，jq 取回结果
git status | claude -p "explain these changes?" \
  --allowedTools '[]' --output-format json | jq .result

# 从 GCP 存储桶读一份巨大日志，让 Claude 找出有意思的东西
cat huge-log.txt | claude -p "what's interesting about this log?"

把它当成一个 UNIX 工具：给它一个提示词，它给你 JSON。可以管道输进去、管道输出来，组合是无穷的——这是一个超级智能的 UNIX 工具。我觉得我们连它的皮毛都还没摸到。

—— Boris Cherny

Anthropic 内部怎么用 SDK？

  • CI 流水线——天天在用
  • 事故响应（Incident Response）
  • 各类自动化管道——批量分析、数据加工
12

并行运行多个 Claude

演讲里"最高级的用法"——超级用户的共同习惯：同时跑多个 Claude。

Boris 自嘲是个 "Claude 普通用户"：一次只跑一个 Claude，顶多为几个仓库开几个终端标签页。但无论 Anthropic 内外的高级用户（power users），几乎总是这样工作：

SSH + Tmux 隧道

多个 SSH 会话，用 Tmux 隧道挂着自己的各个 Claude 会话。

同一仓库多份 Checkout

把同一个仓库检出多份副本，在每份副本里并行跑一个 Claude。

Git Worktree 隔离

用 git worktree 在同一仓库中开辟相互隔离的工作树，各自独立改代码。

GitHub Actions 并行

利用 GitHub Actions 让多个 Claude 在云端并行处理 Issue / PR。

官方正在改进

Boris 表示团队正在努力让这类并行用法更容易上手；眼下，上面这些就是与 Claude 并行做更多事情的思路。会话数量不设限，并行能完成大量工作。

Q&A 精华

演讲结束后的现场问答，信息量同样很大。

Q1

开发 Claude Code 的过程中，实现上最难的部分是什么？

A

难点很多，特别棘手的一块是让 Bash 命令安全。Bash 天生危险，会以意想不到的方式改变系统状态；但若每条命令都要人工批准，工程师根本没法高效工作——会不停地被弹窗打断。

而且不是所有人都在 Docker 容器里跑代码，要在各种代码库上做到既安全又可扩展很难。最终方案分三层：① 区分只读命令与修改命令；② 用静态分析判断哪些命令可以安全组合；③ 一套相当复杂的分层权限系统，支持在不同层级对命令做白名单与拦截。

Q2

Claude Code 支持多模态吗？是把图片路径指给它，还是有我不知道的功能？

A

完全多模态，从第一天起就是。因为是终端应用，所以不太容易被发现。三种方式都可以：① 直接把图片拖放进终端；② 给文件路径；③ 复制粘贴图片。

Boris 的典型用法：手头有张设计稿 → 拖进来让它实现 → 再配一个 Puppeteer 服务器供它截图对比迭代——全程全自动。

Q3

为什么做成 CLI 工具而不是 IDE？

A

原因一：兼容性。Anthropic 的人用 VS Code、Zed、Xcode、Vim、Emacs 的都有，很难做出对所有人好用的东西——终端是最大公约数。

原因二：面向未来。他们近距离看着模型进步的速度，认为很可能到年底人们就不再用 IDE 了——所以不想在 UI 和其他叠加层上过度投入，免得那些投入很快失去价值。

Q4

在机器学习 / 建模这类场景里，Claude Code 用得怎么样？

A

用得很多。Anthropic 的工程师和研究员每天都在用——大约 80% 的 Anthropic 技术人员每天使用 Claude Code，包括研究员：他们会用 notebook 工具来编辑和运行 Jupyter Notebook。"希望你们能从产品里看到我们投入的爱和自吃狗粮（dog-fooding）。"

学习路线图：从入门到精通

把整场演讲浓缩为一条可执行的进阶路径。

阶段一 · 今天就能做

安装并完成基础设置

安装 Claude Code → 运行 /terminal-setup、/theme → 配好 /allowed-tools → （macOS）开启语音听写。

阶段二 · 第一周

只做代码库问答，先别改代码

对代码库疯狂提问：这段代码怎么用、为什么这样设计、翻 Git 历史、生成本周交付清单。建立提示词手感与能力边界的直觉。

阶段三 · 开始动手

编辑代码，掌握工作流

先规划再编码 → 学会 commit push 一键提交 → 按任务选择三大工作流 → 永远给它一个能检验自身的反馈工具（测试 / 截图）→ 熟记快捷键。

阶段四 · 团队工程化

写 CLAUDE.md，接入团队工具

编写精炼的项目 CLAUDE.md（常用命令、架构决策、风格指南）→ 接入 Bash CLI 与 MCP 工具 → 把 .mcp.json、斜杠命令、权限配置提交进仓库共享 → 用 /memory 管理。

阶段五 · 高级玩法

SDK 集成与并行协作

用 claude -p 把 Claude 嵌进 CI / 事故响应 / 数据管道 → 多 checkout / git worktree / Tmux 并行跑多个 Claude。

贯穿全场的心法清单

  • 上下文越多，表现越好——花时间调优 CLAUDE.md 与工具配置，"做对了，性能会有戏剧性的提升"
  • 给 Claude 一个反馈循环——测试、截图、任何能检验工作的手段，它就会自己迭代到近乎完美
  • 先规划，后编码——"写代码之前先做个计划"，一句提示就能避免 3000 行返工
  • 配置一次，全组受益——从项目共享层开始，形成团队网络效应
  • 像用同事一样用它——直接说话、给上下文、提要求，不必微操每个工具调用
